В [[Драйвер внешней периферии|прошлом занятии]] мы разобрались с драйверами и разделением логики устройства на платформонезависимую и платформозависимую части. Вы научились работать с регистрами периферии и общаться с внешними устройствами через SPI и I2C. Но как организовать код, когда проект растёт? Где граница между «понятной» работой с регистрами и «правильной» архитектурой? В этой статье разберём уровни абстракции во встроенном ПО — подходы, которые используют в промышленности и описывают в академических работах.

> [!NOTE] Определение
>  **Абстракция во встроенных системах** — принцип, согласно которому некоторая часть системы берёт на себя ответственность по реализации определённого функционала и скрывает детали его реализации, предоставляя пользователю интерфейс для использования этого функционала.

>[!NOTE] Определение
>**Уровни абстракции во встроенных системах** — представление системы как иерархически связанных абстрактных частей, каждая из которых использует функционал частей нижнего уровня и не имеет доступа к их деталям реализации.

| Уровень           | Содержание                            | Пример                                    |
| ----------------- | ------------------------------------- | ----------------------------------------- |
| **Физический**    | Физический разъём, распиновка         | MikroBus, pin header                      |
| **Процессорный**  | Уровни логики, подтяжки, ёмкость шины | 3.3 В, pull-up на SDA/SCL                 |
| **Платформенный** | Тайминги, адресация, ACK/NACK         | I2C 7-bit адрес, частота 400 кГц          |
| **Протокольный**  | Программный API протокола             | `I2C_writeBytes`, `UART_writeBytes`       |
| **Драйверный**    | Команды и данные устройства           | `SensorX_getValue`, `SensorX_sendCommand` |
| **Прикладной**    |                                       |                                           |
## Зачем нужны уровни абстракции

Работа с регистрами — основа программирования микроконтроллеров. Вы уже видели, как `*ptr = value` или вызовы вроде `i2c_read_blocking()` выполняют низкоуровневую работу. Но когда в проекте десятки датчиков, дисплеев и протоколов, код быстро превращается в «большой ком грязи» (*big ball of mud*): всё связано со всем, изменения в одном месте ломают другое, а новая функциональность требует правок в нескольких модулях.

Уровни абстракции — это способ **разделить знания** о системе. Верхний слой знает, *что* нужно сделать (прочитать температуру), нижний — *как* это сделать аппаратно (какие биты в какие регистры записать). Между ними — промежуточные слои, каждый из которых скрывает детали нижележащего.

## Пять уровней при работе с последовательной шиной

Документация Microchip (в контексте отладки последовательной связи) выделяет пять уровней абстракции. Эта модель полезна для понимания, где локализовать проблему при отладке.

| Уровень           | Содержание                            | Пример                                    |
| ----------------- | ------------------------------------- | ----------------------------------------- |
| **Механический**  | Физический разъём, распиновка         | MikroBus, pin header                      |
| **Электрический** | Уровни логики, подтяжки, ёмкость шины | 3.3 В, pull-up на SDA/SCL                 |
| **Протокольный**  | Тайминги, адресация, ACK/NACK         | I2C 7-bit адрес, частота 400 кГц          |
| **Драйверский**   | Программный API протокола             | `I2C_writeBytes`, `UART_writeBytes`       |
| **Прикладной**    | Команды и данные устройства           | `SensorX_getValue`, `SensorX_sendCommand` |

Ошибка может возникнуть на любом уровне. Если датчик не отвечает, причина может быть в неправильной распиновке (механика), отсутствии подтяжек (электрика), неверном адресе (протокол), ошибке в функции обмена (драйвер) или в логике запроса (приложение). Понимание уровня абстракции сужает область поиска.

## Архитектура прошивки: LL, HAL, Driver, Application

В документации производителей (Espressif ESP-IDF, Silicon Labs, Intel) и в профессиональной практике используется типичная структура из трёх-четырёх слоёв.

```
┌─────────────────────────────────────────────────────────────┐
│  Прикладной слой (Application)                              │
│  Бизнес-логика, конечные автоматы, оркестрация задач        │
│  Не содержит обращений к регистрам                          │
└─────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Драйверы / Сервисы                                          │
│  Протоколы устройств: BME280_get_temperature, display_fill  │
│  Используют HAL, не знают регистров MCU                      │
└─────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  HAL (Hardware Abstraction Layer)                            │
│  Абстракция периферии: hal_spi_transfer(), hal_i2c_read()   │
│  Скрывает различия между семействами MCU                      │
└─────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  LL (Low Level) / Регистровый уровень                       │
│  Обёртки над регистрами: xxx_ll_set_baud_rate()             │
│  Прямая работа с полями регистров периферии                 │
└─────────────────────────────────────────────────────────────┘
                              ▼
                         Аппаратура
```

**LL (Low Level)** — функции, которые заменяют ручную работу с битами и сдвигами. Вместо `hw->clk_div_reg.divider = (freq / baud) >> 4` вызывается `xxx_ll_set_baud_rate(hw, clock_source, baud_rate)`. LL остаётся привязанным к конкретному чипу, но читаемость и поддерживаемость выше.

**HAL (Hardware Abstraction Layer)** — слой, скрывающий отличия между микроконтроллерами. Приложение вызывает `hal_spi_transfer()`, а реализация внутри решает, использовать ли SPI0 RP2040 или SPI STM32. Переход на другой MCU требует изменить только HAL, а не весь код выше.

**Драйверы** — работают через HAL и реализуют протокол конкретного устройства. Драйвер BME280 знает, какие регистры датчика читать и как пересчитывать сырые данные в температуру, но не знает, на каком пине висит I2C.

**Прикладной слой** — оркестрирует действия: «раз в секунду прочитать датчик и отправить на дисплей». Здесь нет знаний о регистрах, SPI или I2C.

## BSP — слой платы

Между HAL и приложением иногда вводят **BSP (Board Support Package)** — слой, описывающий, как устройство подключено физически. «Светодиод на GP25», «BME280 на I2C0, адрес 0x76» — это знание BSP. BSP вызывает функции HAL с нужными параметрами и изолирует приложение от изменений разводки платы.

## Академический подход: Abstraction Layered Architecture (ALA)

Статья *«Abstraction Layered Architecture: Writing Maintainable Embedded Code»* (Spray, Sinha, ECSA 2018, Springer) и последующие публикации в IEEE Transactions on Software Engineering описывают референсную архитектуру ALA для долгосрочной поддерживаемости встраиваемого ПО.

ALA предлагает четыре слоя, от общего к частному:

1. **Language** — язык программирования и стандартные библиотеки.
2. **Framework** — парадигмы программирования (событийная модель, таймеры) и общие сервисы.
3. **Domain Abstractions** — доменные абстракции, пригодные для всех приложений в предметной области.
4. **Application** — конкретное приложение как композиция экземпляров доменных абстракций.

Ключевые принципы ALA:

- **Зависимости направлены только вниз** — верхний слой зависит от нижнего, никогда наоборот.
- **Композиция, а не коллаборация** — модули соединяются через композицию, без взаимного знания о внутренностях друг друга.
- **Разделение требований и реализации** — требования выражаются в терминах доменных абстракций, реализация скрыта в нижних слоях.

Исследование на коммерческом продукте показало улучшение модульности, переиспользуемости, анализируемости и тестируемости при переходе на ALA.

## Главный принцип: зависимости только вниз

Во всех описанных подходах действует одно правило: **верхние слои зависят от нижних, нижние не знают о верхних**. Это позволяет:

- менять реализацию (другой MCU, другая плата) без правок в прикладном коде;
- тестировать слои по отдельности, подменяя зависимости;
- понимать код: при чтении модуля достаточно знать только интерфейсы слоёв под ним.

>[!NOTE] Из практики
>В Pico SDK вы уже видели подобное разделение: `i2c_read_blocking()` — это уровень, скрывающий регистры I2C. Драйвер BME280 использует эти функции и не обращается к регистрам напрямую. В крупных проектах добавляют свой HAL между драйверами и SDK, чтобы при смене MCU менять только один слой.

## Итог

Уровни абстракции во встроенном ПО — это способ структурировать код так, чтобы знания о железе не расползались по всему проекту. Промышленность использует модели вроде LL → HAL → Driver → Application. Академические работы (ALA) усиливают эти идеи принципами композиции и строгой направленности зависимостей.

В следующих статьях мы применим эти идеи на практике: построим простой HAL для наших проектов и посмотрим, как он упрощает перенос кода и добавление новой функциональности.
