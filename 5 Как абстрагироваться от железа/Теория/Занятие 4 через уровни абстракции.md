На прошлом занятии вы построили систему, которая считывает температуру, давление и влажность с датчика BME280, пересчитывает «сырые» отсчёты в физические величины и передаёт их на ПК по USB. Это была самая объёмная практическая работа в курсе: несколько библиотек, драйвер с двумя слоями, карта регистров, компенсационные формулы. Теперь давайте оглянёмся назад и посмотрим на это занятие глазами архитектора — через призму уровней абстракции.

Цель этой статьи — не повторить материал занятия, а показать, что каждое решение, принятое на занятии 4, было мотивировано конкретным уровнем абстракции. Понимание этой связи поможет вам применять тот же подход в новых задачах.

## Физический уровень: разъёмы, пины и подтяжки

Прежде чем написать хотя бы строчку кода, нужно было ответить на вопросы: куда подключить датчик, хватит ли напряжения, нужны ли подтяжки. Это и есть **физический уровень**.

Датчик BME280 работает с уровнями 3,3 В — как и RP2040. Соединение по I2C требует двух линий: SDA и SCL. Чтобы линии не «зависали» в неопределённом состоянии, на них устанавливают подтягивающие резисторы к питанию. В рамках занятия вы подключали BME280 через макетную плату и соединительные провода к пинам GP4 (SDA) и GP5 (SCL) платы Raspberry Pi Pico.

```text
RP2040 (Pico)           BME280
   GP4 (SDA) ──[4.7 кОм]── VDD
   GP5 (SCL) ──[4.7 кОм]── VDD
   GP4 (SDA) ────────────── SDA
   GP5 (SCL) ────────────── SCL
   3V3 OUT   ────────────── VDD
   GND       ────────────── GND
              ────────────── CSB → VDD  (режим I2C)
              ────────────── SDO → GND  (адрес 0x76)
```

Программист, который будет работать на уровне выше, знает только одно: «BME280 на I2C0, адрес 0x76». Как проведены провода, какие резисторы стоят, допустима ли длина шлейфа — это знание физического уровня. Он уже выполнен, и на него можно опереться.

## Процессорный уровень: тулчейн и компилятор

На занятии вы работали с Pico SDK и CMake, не задумываясь о том, как именно процессор Cortex-M0+ исполняет инструкции, как устроен его конвейер и какой у него набор команд. Всё это — зона ответственности **процессорного уровня**, которую закрывают компилятор `arm-none-eabi-gcc` и стартовый код SDK.

Вы лишь указывали в `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.13)
include($ENV{PICO_SDK_PATH}/external/pico_sdk_import.cmake)
project(04-bme C CXX ASM)
pico_sdk_init()
```

Этой строчки достаточно, чтобы компилятор знал: цель — RP2040, Cortex-M0+, флеш-память 2 МБ. Всё остальное скрыто. Интерфейс этого уровня для вас — язык C и стандартная библиотека.

## Платформенный уровень: I2C через Pico SDK

Когда физический уровень корректен и тулчейн настроен, вы получаете доступ к периферии микроконтроллера. Это **платформенный уровень**, за который отвечает Pico SDK.

На занятии вы инициализировали I2C одним блоком:

```c
i2c_init(i2c0, 400 * 1000);          /* Fast mode: 400 кГц */
gpio_set_function(4, GPIO_FUNC_I2C);
gpio_set_function(5, GPIO_FUNC_I2C);
gpio_pull_up(4);
gpio_pull_up(5);
```

После этих пяти строк вы получаете готовый I2C-контроллер, не вникая в регистры `I2C_CON`, `I2C_TAR`, `I2C_DATA_CMD`. Функции `i2c_write_blocking()` и `i2c_read_blocking()` — это и есть интерфейс платформенного уровня.

> [!NOTE] Из практики
> Именно на этом уровне часто ищут ошибки при отладке. Датчик не отвечает? Сначала проверяйте физический уровень (подтяжки, адрес), затем — платформенный: правильно ли вызвана `i2c_init()`, верно ли указан идентификатор шины. Только убедившись, что I2C работает и устройство отвечает на адрес, переходите выше.

## Протокольный и драйверный уровень: BME280

Зная, что I2C работает, можно общаться с датчиком. Здесь начинается **протокольный и драйверный уровень** — самая объёмная часть занятия 4.

### Протокол чтения и записи регистров

Протокольный уровень для I2C описывает формат транзакции. Чтобы прочитать регистр BME280:

1. Отправить адрес устройства (0x76) в режиме записи.
2. Отправить номер регистра.
3. Переключиться в режим чтения и принять байт(ы).

Для записи — аналогично, но без переключения на чтение: адрес устройства → номер регистра → значение.

```c
/* Чтение N байт начиная с регистра reg */
static int bme280_read_regs(bme280_ctx_t *ctx, uint8_t reg,
                             uint8_t *buf, size_t len) {
    int ret = i2c_write_blocking(i2c0, ctx->i2c_addr, &reg, 1, true);
    if (ret < 0) return ret;
    return i2c_read_blocking(i2c0, ctx->i2c_addr, buf, len, false);
}
```

Этот фрагмент реализует именно протокольный слой: он знает формат транзакции I2C, но не знает смысла конкретных регистров.

### Драйвер: команды и конфигурация

Поверх протокола вы строили драйвер — код, который знает конкретное устройство: адреса регистров, смысл их полей, формулы пересчёта.

На занятии вы настраивали три регистра, чтобы перевести датчик в нормальный режим:

| Регистр | Адрес | Значение | Что настраивает |
| --- | --- | --- | --- |
| `ctrl_hum` | 0xF2 | 0x01 | Оверсемплинг влажности ×1 |
| `ctrl_meas` | 0xF4 | 0x27 | Т ×1, P ×1, Normal mode |
| `config` | 0xF5 | 0xA0 | Standby 1000 мс, IIR off |

Драйвер скрывает эти детали за функциями `bme280_init()`, `bme280_read_temp_raw()`, `bme280_read_pressure_raw()`. Прикладной код не знает ни адресов регистров, ни значений полей.

### Платформонезависимость: контекст драйвера

Ключевое решение занятия 4 — разделение драйвера на логику и платформу. В статье [[Драйвер внешней периферии]] это оформлено через **контекст драйвера** (*driver context*): структуру, которая содержит функции-коллбэки для записи и чтения по I2C.

```c
typedef struct {
    uint8_t  i2c_addr;
    int    (*write)(uint8_t addr, uint8_t reg, const uint8_t *data, size_t len);
    int    (*read) (uint8_t addr, uint8_t reg, uint8_t *data, size_t len);
} bme280_ctx_t;
```

Благодаря этому драйвер стал **платформонезависимым**: его можно перенести на STM32 или ESP32, заменив только реализацию коллбэков, но не логику работы с регистрами.

> [!EXAMPLE] Пример
> Если в будущем потребуется работать с BME280 по SPI, достаточно написать новые коллбэки `spi_write` / `spi_read` и передать их в контекст. Логика драйвера — карта регистров, формулы компенсации — не изменится.

## Прикладной уровень: оркестрация и передача данных

Прикладной уровень — это код, который выполняет задачу устройства, не зная об аппаратных деталях. На занятии 4 прикладной уровень состоял из двух частей.

**Цикл измерений:** раз в секунду читать температуру, давление и влажность через драйвер и выводить их в USB-консоль.

```c
while (true) {
    float temp = bme280_read_temperature(&ctx);
    float pres = bme280_read_pressure(&ctx);
    float hum  = bme280_read_humidity(&ctx);
    printf("T=%.2f C, P=%.1f Pa, H=%.1f %%\n", temp, pres, hum);
    sleep_ms(1000);
}
```

Здесь нет ни `i2c_write_blocking`, ни адресов регистров, ни компенсационных формул. Прикладной код видит только три числа.

**Python-скрипт для построения графиков:** читает строки из Serial-порта и строит графики в реальном времени. Это тоже прикладной уровень, но уже на стороне ПК — он знает только формат строки (`T=%.2f C, P=%.1f Pa, H=%.1f %%`) и ничего о физических уровнях ниже.

## Занятие 4 целиком: карта уровней

Взглянем на всю систему разом:

```text
┌─────────────────────────────────────────────┐
│  Прикладной уровень                          │
│  while-цикл: bme280_read_temperature()       │
│  Python-скрипт: графики по Serial            │
├─────────────────────────────────────────────┤
│  Драйверный уровень                          │
│  bme280_init(), bme280_read_*()              │
│  карта регистров, компенсационные формулы    │
├─────────────────────────────────────────────┤
│  Протокольный уровень                        │
│  bme280_read_regs(), bme280_write_reg()      │
│  формат I2C-транзакции: адрес → рег → байты  │
├─────────────────────────────────────────────┤
│  Платформенный уровень                       │
│  i2c_init(), i2c_write_blocking()            │
│  Pico SDK, регистры I2C-контроллера RP2040   │
├─────────────────────────────────────────────┤
│  Процессорный уровень                        │
│  arm-none-eabi-gcc, CMake, Cortex-M0+        │
├─────────────────────────────────────────────┤
│  Физический уровень                          │
│  GP4/GP5, подтяжки 4.7 кОм, VDD 3.3 В       │
└─────────────────────────────────────────────┘
```

Каждый уровень использует только функции уровня ниже и скрывает свои детали от уровня выше. Именно так выглядит правильно построенная иерархия абстракций.

## Что происходит при нарушении уровней

На занятии 4 вы также видели, как выглядит **нарушение уровней абстракции**. Если прикладной код напрямую вызывает `i2c_write_blocking()` с адресом регистра `0xF4` и значением `0x25` — это нарушение: прикладной уровень залезает в детали протокольного и даже платформенного уровня.

Такой код работает, но становится невозможно:

- переключить датчик с I2C на SPI, не переписывая прикладной код;
- сменить микроконтроллер, не трогая логику приложения;
- быстро найти ошибку, потому что непонятно, на каком уровне она лежит.

Именно поэтому на занятии вы выносили работу с регистрами в драйвер, а платформенные вызовы — в отдельный слой с коллбэками.
